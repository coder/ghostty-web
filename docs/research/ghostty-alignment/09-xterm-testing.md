## 1. Executive findings

1. **No screenshot-golden suite was found in the inspected tests.** No test calls `toHaveScreenshot` or `toMatchSnapshot` (`evidence/counts.md`). Its "visual" tests are **analytic colour probes**:
   - Playwright captures a PNG of `.xterm-screen`, decodes it, and reads **one pixel at the centre of a cell** ([`SharedRendererTests.ts#L1514-L1545`](https://github.com/xtermjs/xterm.js/blob/c58ea3637f3968e0e6e79cd92cf9aace7ef89ee2/test/playwright/SharedRendererTests.ts#L1514-L1545)).
   - Expected values are distinctive theme colours such as `#010203` drawn with `■` ([`#L30-L51`](https://github.com/xtermjs/xterm.js/blob/c58ea3637f3968e0e6e79cd92cf9aace7ef89ee2/test/playwright/SharedRendererTests.ts#L30-L51)).
   - The WebGL atlas tests compare **in-run before/after** cell signatures (a 4×4 grid of channel means, maximum difference ≤ 14) ([`WebglAtlasOverflow.test.ts#L263-L324`](https://github.com/xtermjs/xterm.js/blob/c58ea3637f3968e0e6e79cd92cf9aace7ef89ee2/addons/addon-webgl/test/WebglAtlasOverflow.test.ts#L263-L324)).
   - No committed reference-image workflow was found for these suites.
2. **The techniques overlap ours.** Our per-cell comparator checks a larger pixel area than their centre-only colour probes. That does not mean our overall coverage is broader.
3. **xterm's pixel probes have two weaknesses we should not copy:**
   - **Stale-frame polling.** The screenshot is cached in a module-level `frameDetails` (`??=`, [`#L1515`](https://github.com/xtermjs/xterm.js/blob/c58ea3637f3968e0e6e79cd92cf9aace7ef89ee2/test/playwright/SharedRendererTests.ts#L1515), [`#L1524-L1534`](https://github.com/xtermjs/xterm.js/blob/c58ea3637f3968e0e6e79cd92cf9aace7ef89ee2/test/playwright/SharedRendererTests.ts#L1524-L1534)), so `pollFor` retries re-read the **same** image ([`TestUtils.ts#L529-L571`](https://github.com/xtermjs/xterm.js/blob/c58ea3637f3968e0e6e79cd92cf9aace7ef89ee2/test/playwright/TestUtils.ts#L529-L571)). Tests must reset it by hand after each state change. Readiness is really "write callback, then one screenshot".
   - **Silent renderer fallback.** The WebGL addon is loaded inside `try {} catch (e) {}` ([`WebglRenderer.test.ts#L17-L22`](https://github.com/xtermjs/xterm.js/blob/c58ea3637f3968e0e6e79cd92cf9aace7ef89ee2/addons/addon-webgl/test/WebglRenderer.test.ts#L17-L22)). If WebGL fails, the "WebGL" suite runs against the DOM renderer and can still pass.
4. **Our main pain points are mostly not tested through pixels or real interactions upstream:**
   - **Wheel:** every integration wheel check is commented out (0 active, 47 commented `await wheel…` lines; [`MouseTracking.test.ts#L255-L261`](https://github.com/xtermjs/xterm.js/blob/c58ea3637f3968e0e6e79cd92cf9aace7ef89ee2/test/playwright/MouseTracking.test.ts#L255-L261)).
   - **Scrollbar, smooth scrolling, runtime `fontFamily` rendering:** no tests found.
   - **Scrollback, selection semantics, wide/emoji words, soft wraps and reflow:** tested mainly as buffer/model **unit** tests.
   - **Rendered selection:** colours are pixel-tested only after **programmatic** `selectAll()`/`selectLines()`, not after a real drag.
5. **No performance-budget job was found in CI.** `xterm-benchmark` runs manually with relative baseline tolerances ([`benchmark.json`](https://github.com/xtermjs/xterm.js/blob/c58ea3637f3968e0e6e79cd92cf9aace7ef89ee2/test/benchmark/benchmark.json)) and is not in CI. The demo has a manual "Load test" that prints MiB/s ([`testWindow.ts#L681-L710`](https://github.com/xtermjs/xterm.js/blob/c58ea3637f3968e0e6e79cd92cf9aace7ef89ee2/demo/client/components/window/testWindow.ts#L681-L710)). The examined test timeouts are completion/readiness limits, not responsiveness budgets.
6. **CI really runs browsers, but narrowly** (§5):
   - Linux only; integration on macOS is disabled as flaky.
   - Chromium, Firefox and WebKit in a matrix.
   - Several renderer suites are skipped on WebKit/Firefox; the synchronized-output pixel tests are skipped everywhere as "too flaky".
7. **Bottom line:** xterm.js is a useful **compatibility** reference for API/event semantics and selection word rules. It is not a correctness oracle for rendering, scrollback or VT behaviour; that remains Ghostty plus spec, as in our oracle policy. The ideas worth adopting are its **colour-coded content trick** and its **runtime-theme-then-probe** pattern, applied to our scrollback and selection gaps (§7).

## 3. Visual mechanics, inspected

- **Capture:** `page.locator('#terminal-container .xterm-screen').screenshot()`, decoded with `@lunapaint/png-codec` (MIT). Cell size is `image.width / cols` (fractional). The probe reads the **centre pixel**, or for one cursor-outline check the first pixel, of 1-based cells ([`#L1536-L1556`](https://github.com/xtermjs/xterm.js/blob/c58ea3637f3968e0e6e79cd92cf9aace7ef89ee2/test/playwright/SharedRendererTests.ts#L1536-L1556)).
  - Comparison is exact RGBA (`deepStrictEqual`).
  - `pollForApproximate` adds a per-channel margin for minimum-contrast and dim tests ([`TestUtils.ts#L574-L597`](https://github.com/xtermjs/xterm.js/blob/c58ea3637f3968e0e6e79cd92cf9aace7ef89ee2/test/playwright/TestUtils.ts#L574-L597)).
  - Centre sampling cannot detect missing accent ink, seams, partial erasure or offsets of less than half a cell. Our per-cell comparator, incremental-versus-full check and seam probes exist precisely for those.
- **Goldens:** no screenshot-baseline suite, baseline-update workflow or image masks were found in the inspected tests. With `DEBUG` set, a screenshot is written for local diagnosis only ([`#L1526`](https://github.com/xtermjs/xterm.js/blob/c58ea3637f3968e0e6e79cd92cf9aace7ef89ee2/test/playwright/SharedRendererTests.ts#L1526)).
- **Fonts:** not pinned. The test page sets no terminal font ([`demo/test.html`](https://github.com/xtermjs/xterm.js/blob/c58ea3637f3968e0e6e79cd92cf9aace7ef89ee2/demo/test.html)), and `openTerminal` passes only caller options ([`TestUtils.ts#L449-L518`](https://github.com/xtermjs/xterm.js/blob/c58ea3637f3968e0e6e79cd92cf9aace7ef89ee2/test/playwright/TestUtils.ts#L449-L518)). This is tolerable only because probes sit in the middle of `■` or background cells.
  - The repo's fonts are **BPdots (CC BY-ND)** and **Kongtext (custom, no resale)** ([`demo/fonts/font-licenses.txt`](https://github.com/xtermjs/xterm.js/blob/c58ea3637f3968e0e6e79cd92cf9aace7ef89ee2/demo/fonts/font-licenses.txt)). They are used only by the web-fonts addon test, which asserts `document.fonts` status, not rendering ([`WebFontsAddon.test.ts#L98-L131`](https://github.com/xtermjs/xterm.js/blob/c58ea3637f3968e0e6e79cd92cf9aace7ef89ee2/addons/addon-web-fonts/test/WebFontsAddon.test.ts#L98-L131)). **Do not vendor them.**
- **Browser, DPR, container:**
  - No `deviceScaleFactor`, viewport, container or OS pinning in the core config, which uses Playwright defaults ([`playwright.config.ts#L3-L33`](https://github.com/xtermjs/xterm.js/blob/c58ea3637f3968e0e6e79cd92cf9aace7ef89ee2/test/playwright/playwright.config.ts#L3-L33)).
  - CI uses `npm ci`; `package-lock.json` pins `@playwright/test`, `playwright` and `playwright-core` to **1.60.0**, which selects the installed browser revisions. Browsers are then installed per job with `npx playwright install --with-deps`. The manifest range is `^1.59.1` ([`package.json`](https://github.com/xtermjs/xterm.js/blob/c58ea3637f3968e0e6e79cd92cf9aace7ef89ee2/package.json)).
- **Animation:** cursor blink defaults off. Theme, `minimumContrastRatio` and transparency are reset before each test ([`#L18-L27`](https://github.com/xtermjs/xterm.js/blob/c58ea3637f3968e0e6e79cd92cf9aace7ef89ee2/test/playwright/SharedRendererTests.ts#L18-L27)).
- **Readiness:**
  - `proxy.write` awaits xterm's write callback ([`TestUtils.ts#L277-L281`](https://github.com/xtermjs/xterm.js/blob/c58ea3637f3968e0e6e79cd92cf9aace7ef89ee2/test/playwright/TestUtils.ts#L277-L281)); `pollFor` polls every 10 ms, up to **2,000 ms**.
  - Fixed sleeps remain: `timeout(20)`/`timeout(100)` in `Terminal.test.ts`, 224 `timeout(…)` calls in `KittyGraphics.test.ts`, and `waitForTimeout(50)` in atlas loops ([`WebglAtlasOverflow.test.ts#L362`](https://github.com/xtermjs/xterm.js/blob/c58ea3637f3968e0e6e79cd92cf9aace7ef89ee2/addons/addon-webgl/test/WebglAtlasOverflow.test.ts#L362)).
- **Retries and artifacts:** no `retries` setting (Playwright default 0); `reporter: 'list'`; no trace or screenshot-on-failure configuration; `reuseExistingServer: !process.env.CI` ([`#L26-L32`](https://github.com/xtermjs/xterm.js/blob/c58ea3637f3968e0e6e79cd92cf9aace7ef89ee2/test/playwright/playwright.config.ts#L26-L32)). Pixel failures report only "last comparison" values from the probe.
- **Quarantine:** 77 skip lines in the Playwright suites. Most are unimplemented sequences. The visual ones are:
  - synchronized output ("TODO: These tests are a little too flaky atm", [`#L1296-L1297`](https://github.com/xtermjs/xterm.js/blob/c58ea3637f3968e0e6e79cd92cf9aace7ef89ee2/test/playwright/SharedRendererTests.ts#L1296-L1297));
  - invisible-background cases ([`#L173`](https://github.com/xtermjs/xterm.js/blob/c58ea3637f3968e0e6e79cd92cf9aace7ef89ee2/test/playwright/SharedRendererTests.ts#L173), [`#L340`](https://github.com/xtermjs/xterm.js/blob/c58ea3637f3968e0e6e79cd92cf9aace7ef89ee2/test/playwright/SharedRendererTests.ts#L340), [`#L721`](https://github.com/xtermjs/xterm.js/blob/c58ea3637f3968e0e6e79cd92cf9aace7ef89ee2/test/playwright/SharedRendererTests.ts#L721));
  - DOM-renderer exceptions;
  - the whole DOM-renderer suite on WebKit ([`Renderer.test.ts#L24`](https://github.com/xtermjs/xterm.js/blob/c58ea3637f3968e0e6e79cd92cf9aace7ef89ee2/test/playwright/Renderer.test.ts#L24)).

## 5. What CI actually runs

From [`.github/workflows/ci.yml`](https://github.com/xtermjs/xterm.js/blob/c58ea3637f3968e0e6e79cd92cf9aace7ef89ee2/.github/workflows/ci.yml), triggered on push and PR to `master`:

- **Jobs:** `build`, `lint`, `test-unit-coverage`, `test-unit` (ubuntu/macOS/windows), `test-integration` (`ubuntu-22.04` × chromium/firefox/webkit, [`#L175-L183`](https://github.com/xtermjs/xterm.js/blob/c58ea3637f3968e0e6e79cd92cf9aace7ef89ee2/.github/workflows/ci.yml#L175-L183)) and `release-dry-run`.
- **Integration runs:** core plus 12 addon suites, each with `--workers=50% --forbid-only` ("Tests use 50% workers to reduce flakiness", [`#L214-L238`](https://github.com/xtermjs/xterm.js/blob/c58ea3637f3968e0e6e79cd92cf9aace7ef89ee2/.github/workflows/ci.yml#L214-L238)). macOS integration is excluded ("macos is flaky", [`#L181`](https://github.com/xtermjs/xterm.js/blob/c58ea3637f3968e0e6e79cd92cf9aace7ef89ee2/.github/workflows/ci.yml#L181)).
- **Not present:** no `continue-on-error`, path filters, retries or benchmark job.
- **Actual browser coverage:** because CI is Linux-only and WebGL is skipped on Linux Firefox/WebKit ([`WebglRenderer.test.ts#L30-L32`](https://github.com/xtermjs/xterm.js/blob/c58ea3637f3968e0e6e79cd92cf9aace7ef89ee2/addons/addon-webgl/test/WebglRenderer.test.ts#L30-L32)), **WebGL pixels run only on Chromium/SwiftShader**. - **What blocks merges is unknown:** `gh api …/branches/master/protection` returned 404 and `rules/branches/master` returned `[]`. That is consistent with no ruleset visible to us, but branch protection may be hidden by permissions. Source proves only what runs, not what blocks.

## 6. Performance

- **Benchmarks:** `xterm-benchmark -r 5`, with `--baseline` and `--eval`. Tolerances are relative to a stored local baseline: `*` within [0.75, 1.5], parser throughput within [0.9, 5]; medians and runs are skipped.
  - These are **manual regression reports, not CI gates**, and they cover parser/`write` throughput only.
  - There is nothing on input-to-paint, smooth scrolling, selection-drag frame cost or render scaling with large history.
- **Timeouts:** the Playwright `timeout: 10000`, `pollFor`'s 2,000 ms and the 90 s atlas timeout are **readiness/test limits**, not speed assertions.
- **Noise:** there is no noise management beyond five benchmark runs, apart from the reduced worker count used to fight flakiness.

## 7. What ghostty-web should do

### Adopt now (first five extensions, all in `tests/browser`, analytic, no goldens)

1. **Wheel through deep history, verified by colour-coded rows.** Write 500 lines, each with a unique truecolor background cell (`48;2;r;g;b` derived from the line number). This adapts xterm's distinct-colour idea from palette slots to row identity.
   - Act: real `page.mouse.wheel` over the canvas, with mouse tracking off.
   - Wait: for a viewport-state predicate, or construct with `smoothScrollDuration: 0` so there is no animation to wait for.
   - Assert: `viewportY`, and that viewport row 0 has the colour of the expected history line. Repeat after scrolling back down.
   - This is font-independent and exact, and catches wrong-row and stale-row rendering, which is our real historical pain.
   - Oracle: an exact line mapping derived from the expected scroll position. xterm.js has no test for this.
2. **Scrollbar drag.** `page.mouse` drag on our canvas scrollbar strip: assert `viewportY` changes in the right direction, the thumb pixel band moves, and row colours match the new `viewportY`. This is ghostty-web behaviour with nothing upstream to copy; treat it as a product invariant.
3. **Selection across history and new output.** Scroll up, drag across two history rows, then assert:
   - `getSelection()` text;
   - the selection-background probe on exactly those rows (all cells in the dragged range, not just the centre);
   - after writing output that scrolls, behaviour follows the policy.
   - Also include xterm's #4917 case: scroll so the selected row leaves the viewport and assert no highlight paints.
   - Expected text and anchor behaviour come from Ghostty's selection semantics (the correctness reference). xterm's `SelectionModel` trimming is a compatibility check only.
4. **Runtime option metamorphic tests.** Change `theme`, then `fontFamily`/`fontSize`, on an open terminal. Assert its canvas equals, cell by cell and exactly, a fresh terminal constructed with the final options and fed the same bytes.
   - This turns xterm's runtime-theme pattern into a strong, font-agnostic oracle with no golden.
   - This needs an independent option-consumption control: first prove two deliberately different option values produce different expected colours/glyphs/metrics. Comparing runtime state with a fresh terminal alone can miss both paths ignoring the option. For fonts, compare representative glyphs with a separate canvas explicitly using the requested vendored font, rather than only comparing two terminal instances. Our earlier ignored-font mutations failed indirectly; they did not survive the entire suite.
   - Today ghostty-web warns that theme changes after `open()` are unsupported, so the theme case would start as a documented known failure.
5. **Wide, combining and soft-wrap selection through real drags.** Drag across a soft-wrapped line with a wide character at the wrap boundary, and across `e`+U+0301. Assert the copied text (no inserted space or newline) and the highlight cells. xterm's unit rules are a compatibility reference; Ghostty's selection string is authoritative.

### Performance, separately

Add a **nightly, report-only** job:

- keydown→paint latency using rAF timestamps;
- wheel-scroll and drag frame times at 1k/10k/100k history lines;
- fixed browser and container, with medians over N runs compared to a stored baseline using wide relative tolerances (as xterm does for its benchmarks).

Keep PR gates to **deterministic counters** we already favour: rows drawn per idle frame, viewport decodes per frame, resizes per idle frame. Do not gate PRs on wall time.

### Overkill or flaky; skip

- A large whole-terminal golden or cross-browser pixel matrix as the first step. xterm's absence of goldens is not proof they lack value: a small, pinned-environment, reviewed scene set remains a reasonable complement where analytic assertions miss appearance changes.
- Wall-clock budgets on shared runners.
- Making macOS/browser-pixel jobs blocking before characterizing their variance. Keep targeted macOS interaction/IME checks and real-device release validation; upstream's flaky jobs are not a reason to omit that coverage permanently.
- Copying xterm's minimum-contrast and selection-blending colour policies as expectations; they are xterm product choices.
- Centre-pixel-only checks, cached frames inside polling, `try/catch` around renderer setup, and fixed sleeps.

**Reference value by area:**

| Area                                       | xterm.js is a…                                                    |
| ------------------------------------------ | ----------------------------------------------------------------- |
| Public API and event shape                 | Compatibility spec (we promise xterm-like API)                    |
| Selection word and line rules              | Compatibility check; Ghostty decides                              |
| VT semantics and fixtures                  | Compatibility corpus (captured from real xterm, with known skips) |
| Rendering colours, contrast, scrollback UX | Not a correctness oracle                                          |

Recommendations now distinguish evidence about xterm's choices from our own product needs, and require an independent font/option control so two equally wrong render paths cannot pass a comparison.
