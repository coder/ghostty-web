## Executive summary

1. **The ABI shape, not the VT core, sets the per-frame cost [M].** Using the existing patch ABI _optimally_ (one `render_state_update`, one `get_viewport`, decode only dirty rows), a frame in which **one row changed** costs 22–24 µs at 80×24 and 110–119 µs at 200×50 — 64–80% of a full frame (28–34 µs / 142–186 µs) — because the only cell getter returns the whole viewport and re-walks pages and styles in WASM. On current upstream, `row_iterator_next_dirty` + `CELLS_RAW` makes the same frame 3.8–4.4 µs / 6.5–6.9 µs. A pinned patch that exports dirty rows from `RenderState` should close most of that gap; **this is an ABI-shape result, not an argument for rebasing by itself.** Idle frames cost ≤1.1 µs in WASM on both builds, so the idle cost reported in WEB-01 is in the TypeScript loop, not in Ghostty.
2. **Full frames remain the expensive case and are common [M].** Scroll, resize, selection changes and palette changes are full-dirty in both backends. Current upstream with a JS-side style cache costs 1.2–2.1× the patch's bulk getter on full frames (200×50: 210–227 µs vs 142–186 µs). Report 02's ~0.70 ms JavaScriptCore figure for the same decode was produced by a different harness; this report's harness measured 0.21 ms. _(Verification note, [report 06](06-verification.md): changing only the raw-cell reads in report 02's harness from `DataView` to `Uint32Array` lowered that figure to 0.54 ms, not 0.21 ms, so the decoder accounts for about a third of the difference and the rest depends on unisolated harness differences.)_ A packed "resolved row" export upstream is therefore **optional**, to be revisited only after real-browser canvas measurements.
3. **Ghostty already owns the viewport, selection and terminal state that ghostty-web re-implements; the patch does not expose it [S].** At the pinned commit the core has a content-anchored viewport pin, tracked pins (with a `garbage` flag on prune), stable page serials (usable as row ids), `RenderState` with per-row dirty/selection/style/grapheme data, `Screen.select*` + `selectionString`, `ScreenSearch`, and `PageList.scrollbar`. The patch instead re-walks `.active` rows and history by index-from-oldest, so TypeScript keeps scroll position, selection and link state as absolute indices.
4. **TypeScript's absolute row indices are structurally unstable [R].** With ghostty-web's default config (10,000 → bytes) at 80 columns, history **saw-tooths between 566 and 1,154 rows**: every 589 lines a whole 588-row page is pruned, so a stored "absolute row" jumps 588 rows (a row selected as `N0001278` later reads `N0005401`). On current upstream a tracked grid ref follows reflow (screen y 12→13) and reports _no value_ once pruned. This also refines WEB-02: the retained history is not a constant 1,116 lines; it oscillates by one page.
5. **Linear memory per terminal is ~5 MiB at the pinned commit [R].** Creating the first terminal grows linear memory from 1.31 to 6.75 MiB; five filled default terminals use 26.75 MiB; freeing them returns nothing (memory is reused, never shrunk). Current upstream: 1.81 MiB for one filled terminal, 5.31 MiB for five — upstream replaced per-terminal preheated page pools with a module-wide WASM page pool ([`492c26067`](https://github.com/ghostty-org/ghostty/commit/492c26067c9f342f46507ade392cfad2e1400360)). These are linear-memory high-water marks, not process RSS.
6. **Pinned core defects become reachable as soon as more state is exported [R][S].** Reproduced: narrowing without reflow (alternate screen, or DECAWM off) leaves an orphaned wide-character head in the last column (upstream fix [`e6db5b633`](https://github.com/ghostty-org/ghostty/commit/e6db5b633a9ae820fea1620af52dbf87cc7e430c), not in pinned) — already reachable today. Static, latent until exported: `PageList.scroll(.row)` casts to `u16` and jumps to the bottom beyond 65,535 rows ([`5fa37f2b7`](https://github.com/ghostty-org/ghostty/commit/5fa37f2b7e2c38a2837632d4dbc1b0b72401bd05)); `RenderState.linkCells` reads the wrong row even on a single page ([`5a2f5a6b9`](https://github.com/ghostty-org/ghostty/commit/5a2f5a6b9e87d2d3324dbcb4022cb02df4db8d6e), [`26b104c9e`](https://github.com/ghostty-org/ghostty/commit/26b104c9e0cc2c013480cc378cf62836cc24d64f)); viewport-pin fix-ups after row changes/reflow ([`86d5048da`](https://github.com/ghostty-org/ghostty/commit/86d5048dad55f6931b8e35b736b335911f1d1f55), [`815ccb060`](https://github.com/ghostty-org/ghostty/commit/815ccb060b1f983272dab86af6bacb156dfcbfd9)) — those also affected native pinned Ghostty, so exporting scrolling gives ghostty-web native-pinned parity including its bugs.
7. **Recommended ABI (PROPOSED, §6):** a backend-agnostic TypeScript adapter (`CoreBackend`/`CoreTerminal`, §6.8) whose frame model is _header + dirty-row list + row records (row id, flags, selection range, cells with **tagged** colors, full attributes, a stable link key) + side tables_, plus an **event queue drained once per write**. On the pinned backend it is a contiguous WASM-owned frame buffer under `ghostty_web_*` names with an ABI-info/manifest handshake; on current upstream the same frame is assembled in JS from `CELLS_RAW` + a per-row style cache (style ids are page-local) and effect callbacks pushed into a JS queue, except where the current API requires synchronous handling: render holds and clipboard-read responses. Browser clipboard reads are asynchronous, so the latter needs an explicit host policy or an upstream asynchronous response API (see report 06 V-04).
8. **Minimum pinned growth (§7.1):** phase A — RenderState-backed dirty-row frames, Ghostty-owned viewport (delta/top/bottom only, plus the tiny `u16` backport), `default_modes`, color presence + tagged colors, in-place reset, error codes, ABI info, and the `e6db5b633` backport; phase B — selection primitives + formatter text, gated on rebase timing. Rough static estimate: +1,000–1,500 lines of Zig (the current `terminal.zig` is 1,123). **Rebase (§7.2):** almost all of this exists upstream (`ghostty_render_state_*`, `ghostty_terminal_scroll_viewport`, tracked grid refs, `ghostty_terminal_select_*`, `ghostty_search_*`); the residual patch shrinks to hyperlink identity (and the `mouse_shift_capture` getter from report 02), and the build needs Zig 0.16 and a new script.

## 1. Scope, sources and method

**Scope.** Terminal core state and its exposure to JavaScript: page lists, pins and tracked pins, scrolling, resize/reflow, selection and search, cell/grapheme/style/hyperlink extraction, dirty-row and render-state ownership, the JS bridge (`lib/ghostty.ts`) and its copy/allocation/crossing patterns, memory growth and lifetime, and the ABI that should replace today's. Query replies, input encoders and rendering pixels are covered by other reports; they appear here only where they shape the ABI (event queue, mode snapshot).

**Sources read.** `patches/ghostty-wasm-api.patch` (all hunks), `lib/ghostty.ts` (all), `lib/renderer.ts` render path, `lib/selection-manager.ts` coordinate model, `lib/buffer.ts`, `lib/index.ts`; pinned `src/terminal/{PageList,Screen,Terminal,render,page,style,hyperlink,search}.zig`, `src/renderer/generic.zig`; current `include/ghostty/vt/{render,terminal,grid_ref,grid_ref_tracked,point,search,wasm,build_info,formatter}.h`, `src/terminal/c/render.zig`, `src/terminal/render.zig`, `src/terminal/PageList.zig`, `src/datastruct/wasm_page_pool.zig`; the upstream git history between the two commits.

**Probes** (sources and raw JSON in the research artifact directory under `probes/state-wasm/`, all prefixed `sw-`; they reuse report 02's `probes/upstream/vt.mjs` host for the current API). Every probe calls the WASM exports directly; none uses ghostty-web's TypeScript.

### 2.1 Page list, pins and tracked pins

**Pinned core [S].** A `PageList` is a linked list of fixed-capacity pages (`std_capacity` = 215 × 215 cells, [P `page.zig#L1627-L1632`](https://github.com/ghostty-org/ghostty/blob/5714ed07a1012573261b7b7e3ed2add9c1504496/src/terminal/page.zig#L1627-L1632)); each node carries a monotonically increasing `serial` ([P `PageList.zig#L41-L46`](https://github.com/ghostty-org/ghostty/blob/5714ed07a1012573261b7b7e3ed2add9c1504496/src/terminal/PageList.zig#L41-L46), [#L116-L132](https://github.com/ghostty-org/ghostty/blob/5714ed07a1012573261b7b7e3ed2add9c1504496/src/terminal/PageList.zig#L116-L132)). A `Pin` is `{node, y (page-local), x, garbage}` ([#L4000-L4010](https://github.com/ghostty-org/ghostty/blob/5714ed07a1012573261b7b7e3ed2add9c1504496/src/terminal/PageList.zig#L4000-L4010)). Tracked pins live in `tracked_pins` and are updated by every page-list mutation ([#L3179-L3200](https://github.com/ghostty-org/ghostty/blob/5714ed07a1012573261b7b7e3ed2add9c1504496/src/terminal/PageList.zig#L3179-L3200)). When scrollback exceeds its byte budget, `grow()` pops the **whole first page**, re-inserts it as the last page with a **new serial**, and moves tracked pins that pointed into it to the new top-left with `garbage = true` ([#L2440-L2507](https://github.com/ghostty-org/ghostty/blob/5714ed07a1012573261b7b7e3ed2add9c1504496/src/terminal/PageList.zig#L2440-L2507)). Consequences that matter for an ABI:

- `(node.serial, pin.y)` is never reused, so it is a valid **row identity** at the pinned commit without core changes (current upstream uses exactly that encoding for `GhosttyRenderStateRowId`, [C `c/render.zig#L134-L147`](https://github.com/ghostty-org/ghostty/blob/8f0dd3709050b1026f6324368805033197d8b4a5/src/terminal/c/render.zig#L134-L147)).
- Converting a pin to a numeric point is O(pages) ([P `pointFromPin`, #L3262-L3294](https://github.com/ghostty-org/ghostty/blob/5714ed07a1012573261b7b7e3ed2add9c1504496/src/terminal/PageList.zig#L3262-L3294)); `pin(.history{y})` walks forward from the first page ([`pin` #L3163-L3173](https://github.com/ghostty-org/ghostty/blob/5714ed07a1012573261b7b7e3ed2add9c1504496/src/terminal/PageList.zig#L3163-L3173), [`getTopLeft` #L3866-L3896](https://github.com/ghostty-org/ghostty/blob/5714ed07a1012573261b7b7e3ed2add9c1504496/src/terminal/PageList.zig#L3866-L3896)).

**Patch [S].** No pin is ever exposed. Rows are addressed by active-area `y` (`pages.pin(.{ .active = … })`, patch L1049, L1170, L1396, L1423) or by history index counted from the oldest row (`pages.pin(.{ .history = … })`, patch L1258, L1360, L1472).

**TypeScript [S].** `SelectionManager` converts between viewport rows and "absolute rows" with `scrollbackLength + viewportRow - viewportY` and stores the absolute numbers (`lib/selection-manager.ts:85-98`, used at `:130-205`); the renderer and link providers use the same index-from-oldest arithmetic (`lib/renderer.ts:364-382`).

**Evidence [R] (`sw-prune-sawtooth`, pinned + patch, ghostty-web default config, 80×24).** Writing 6,000 lines one by one, `getScrollbackLength()` rises to **1,154** and drops to **566** nine times — every 589 lines, 588 rows (one page) disappear at once. A position stored as `absoluteRow = 100` after line 2,000 read `N0001278`; after 6,000 lines the same index reads `N0005401`. **[R] (`sw-tracked`, current).** A tracked grid ref created on `line010` at screen y 12 moves to y 13 after a 20→10 column reflow (the wrapped line above it now takes three rows) and back to 12 after widening, while the absolute index 12 points at `line009`; after 20,000 more lines with a minimal line budget the tracked ref reports `has_value = false` / `GHOSTTY_NO_VALUE` while the index points at unrelated text (`more18173`).

### 2.2 Viewport and scrolling

**Pinned core [S].** The viewport is `active`, `top` or a tracked `pin` with a cached row offset ([P `PageList.zig#L163-L214`](https://github.com/ghostty-org/ghostty/blob/5714ed07a1012573261b7b7e3ed2add9c1504496/src/terminal/PageList.zig#L163-L214)). `PageList.scroll` supports `active`, `top`, `row`, `delta_row`, `delta_prompt` and `pin` ([#L1945-L2179](https://github.com/ghostty-org/ghostty/blob/5714ed07a1012573261b7b7e3ed2add9c1504496/src/terminal/PageList.zig#L1945-L2179)); `Terminal.scrollViewport` exposes only `top`, `bottom` and `delta` ([P `Terminal.zig#L1417-L1435`](https://github.com/ghostty-org/ghostty/blob/5714ed07a1012573261b7b7e3ed2add9c1504496/src/terminal/Terminal.zig#L1417-L1435)). Pruning keeps the cached offset coherent ([#L2469-L2483](https://github.com/ghostty-org/ghostty/blob/5714ed07a1012573261b7b7e3ed2add9c1504496/src/terminal/PageList.zig#L2469-L2483)) and `scrollbar()` returns `{total, offset, len}` ([#L2255-L2355](https://github.com/ghostty-org/ghostty/blob/5714ed07a1012573261b7b7e3ed2add9c1504496/src/terminal/PageList.zig#L2255-L2355)). `RenderState.update` always renders from `getTopLeft(.viewport)` ([P `render.zig#L267-L268`, #L396-L400](https://github.com/ghostty-org/ghostty/blob/5714ed07a1012573261b7b7e3ed2add9c1504496/src/terminal/render.zig#L262-L400)). Because the viewport pin is anchored to content, output arriving while scrolled up does not move the view — exactly the behaviour WEB-09 says ghostty-web lacks.

**Pinned defect, latent (SW-02) [S].** `scroll(.row = n)` casts the remaining row count to `CellCountInt` (`u16`); if the cast fails it silently jumps to the active area ([P `PageList.zig#L2039-L2045`, #L2060-L2066](https://github.com/ghostty-org/ghostty/blob/5714ed07a1012573261b7b7e3ed2add9c1504496/src/terminal/PageList.zig#L2035-L2083)). Any absolute jump more than 65,535 rows from the nearer end (e.g. dragging a scrollbar in a 140k-row history) lands at the bottom. Fixed upstream in [`5fa37f2b7`](https://github.com/ghostty-org/ghostty/commit/5fa37f2b7e2c38a2837632d4dbc1b0b72401bd05) ([C `PageList.zig#L3367-L3404`](https://github.com/ghostty-org/ghostty/blob/8f0dd3709050b1026f6324368805033197d8b4a5/src/terminal/PageList.zig#L3367-L3404)); the `delta_row` path uses `usize` overflow helpers and is not affected. Current upstream reproduced correctly: `scroll_viewport(ROW, 70000)` on a 140,001-row history gives scrollbar offset 70,000 and first visible row `R70000` [R].

**Patch [S].** No scroll export exists. `ghostty_render_state_get_viewport` reads `.active` rows (patch L1044-1049) rather than the viewport that `RenderState.update` just used, so if anything ever moved Ghostty's viewport, the update and the getter would describe different rows.

**TypeScript [S].** `Terminal.viewportY` counts lines from the bottom and may be fractional for smooth scrolling (`lib/terminal.ts:117-121`); any write while scrolled calls `scrollToBottom()` (`lib/terminal.ts:580-583`). A lines-from-bottom anchor cannot stay on content while output arrives, which is presumably why the forced scroll exists.

**Current [S][R].** `ghostty_terminal_scroll_viewport` (`TOP`/`BOTTOM`/`DELTA`/`ROW`, [C `terminal.h#L3105-L3122`](https://github.com/ghostty-org/ghostty/blob/8f0dd3709050b1026f6324368805033197d8b4a5/include/ghostty/vt/terminal.h#L3105-L3122)); `DATA_SCROLLBAR` is amortised O(1) and meant to be polled per frame ([#L2488-L2505](https://github.com/ghostty-org/ghostty/blob/8f0dd3709050b1026f6324368805033197d8b4a5/include/ghostty/vt/terminal.h#L2488-L2505)); overscan supplies rows above/below the viewport for smooth scrolling ([C `render.h#L97-L163`](https://github.com/ghostty-org/ghostty/blob/8f0dd3709050b1026f6324368805033197d8b4a5/include/ghostty/vt/render.h#L97-L163)), which replaces TypeScript's fractional `viewportY` model.

### 2.3 Resize and reflow

**Pinned core [S].** `Terminal.resize` reflows the primary screen only when DECAWM is on; the alternate screen never reflows ([P `Terminal.zig#L2534-L2565`](https://github.com/ghostty-org/ghostty/blob/5714ed07a1012573261b7b7e3ed2add9c1504496/src/terminal/Terminal.zig#L2534-L2565)). Reflow remaps tracked pins (so `Screen.selection` and the viewport pin follow content); a dimension change makes the next `RenderState.update` a full redraw ([P `render.zig#L290-L295`](https://github.com/ghostty-org/ghostty/blob/5714ed07a1012573261b7b7e3ed2add9c1504496/src/terminal/render.zig#L290-L295)).

**Patch/TS [S].** `ghostty_terminal_resize` discards errors (`catch return`, patch L920-923) while `GhosttyTerminal.resize` updates its own `_cols/_rows` unconditionally (`lib/ghostty.ts:350-357`); no pixel size is passed. TypeScript selection and scroll indices are not remapped (WEB-08).

**SW-01 [R] (`sw-resize-widechar`).** Narrowing without reflow leaves an orphaned wide-character head in the new last column at the pinned commit. Stimulus: 3×2 terminal, `a` + U+4E00 on row 0, `XYZ` on row 1, `ESC[?7l`, resize to 2×2. Pinned + patch reports row 0 as `a/w1 一/w2` — a width-2 cell with no spacer tail and no room for one; current reports `a/n ·/n`. Upstream's commit message for the fix says that the follow-up ICH and `EL 1` then panic in `Screen.clearCells` (a safety-checked-build behaviour) and that `rowWillBeShifted` writes `cells[cols]`; in this ReleaseSmall artifact the same follow-ups neither trapped nor modified row 1, so the observed impact is an invalid grid state (a glyph drawn past the right edge), with possible undetected memory effects. Reachable today: resizing while a full-screen application (alternate screen) shows wide characters at the right edge. Fix: [`e6db5b633`](https://github.com/ghostty-org/ghostty/commit/e6db5b633a9ae820fea1620af52dbf87cc7e430c) (about five changed lines in `PageList.resizeWithoutReflow`).

**Current [S].** `ghostty_terminal_resize(term, cols, rows, cell_w_px, cell_h_px)` returns a result, stores pixel sizes for size reports, ends synchronized output and fires the render-hold end callback ([C `terminal.h#L2900-L2928`](https://github.com/ghostty-org/ghostty/blob/8f0dd3709050b1026f6324368805033197d8b4a5/include/ghostty/vt/terminal.h#L2900-L2928)). Viewport-pin handling during reflow was fixed after the pinned commit ([`815ccb060`](https://github.com/ghostty-org/ghostty/commit/815ccb060b1f983272dab86af6bacb156dfcbfd9)).

### 2.4 Selection and search

### 2.5 Cells, styles, graphemes and hyperlinks

**Pinned core [S].** `page.Cell` is a packed `u64`: content tag (codepoint, codepoint+grapheme, bg-palette, bg-rgb), a **page-local** `style_id`, width class, protected and hyperlink bits ([P `page.zig#L1812`](https://github.com/ghostty-org/ghostty/blob/5714ed07a1012573261b7b7e3ed2add9c1504496/src/terminal/page.zig#L1808-L1850)). Hyperlinks are a page-local `cell → id` map plus a set of `PageEntry {id: explicit | implicit, uri}` compared with `PageEntry.eql` across pages ([P `hyperlink.zig#L79-L90`, #L161-L186](https://github.com/ghostty-org/ghostty/blob/5714ed07a1012573261b7b7e3ed2add9c1504496/src/terminal/hyperlink.zig#L79-L186)); implicit ids come from a per-screen counter ([P `Screen.zig#L2053-L2055`](https://github.com/ghostty-org/ghostty/blob/5714ed07a1012573261b7b7e3ed2add9c1504496/src/terminal/Screen.zig#L2043-L2060)). `RenderState.Cell` is `{raw, grapheme, style}`, but `style` is **undefined unless `raw.style_id != 0`**, and styles/graphemes are only populated for rows whose `managedMemory()` is true; bg-color content tags must be decoded from `raw` ([P `render.zig#L209-L223`, #L505-L551](https://github.com/ghostty-org/ghostty/blob/5714ed07a1012573261b7b7e3ed2add9c1504496/src/terminal/render.zig#L505-L551); `Style.bg` handles this, [P `style.zig#L109-L127`](https://github.com/ghostty-org/ghostty/blob/5714ed07a1012573261b7b7e3ed2add9c1504496/src/terminal/style.zig#L109-L127)). `Style.fg` takes a `bold` option for bold-is-bright/bold colour ([#L145-L175](https://github.com/ghostty-org/ghostty/blob/5714ed07a1012573261b7b7e3ed2add9c1504496/src/terminal/style.zig#L145-L175)).

**Patch [S].** `GhosttyCell` (16 B, patch L773-786) carries resolved RGB fg/bg with no "default" bit, eight flag bits (underline collapsed to a boolean), width, `hyperlink_id` ∈ {0, 1} (patch L1138) and `grapheme_len`. Foreground resolution ignores the `bold` policy (patch L1100-1104). Graphemes and hyperlink URIs need one extra WASM call per cell.

**Current [S].** `CELLS_RAW` returns the packed 8-byte cells of a row in one call; their bit layout is published in the `ghostty_type_json` manifest but "not protected by ABI" ([C `render.h#L446-L460`](https://github.com/ghostty-org/ghostty/blob/8f0dd3709050b1026f6324368805033197d8b4a5/include/ghostty/vt/render.h#L446-L460)). Styles need `row_cells_select` + `STYLE`; `FG_COLOR`/`BG_COLOR` report "no value" for defaults. Hyperlinks: a `has_hyperlink` bit and `ghostty_grid_ref_hyperlink_uri`; there is no identity, so "highlight the hovered link" needs URI comparisons or a residual export.

**Implementation hazard for any JS consumer of raw cells (SW-09) [S].** Because `style_id` is page-local, a style cache keyed only by `style_id` must be scoped to one page (in practice: per row, or per row-id `serial`). A frame-wide `style_id → style` cache would silently mix styles across pages.

### 2.6 Dirty tracking and render-state ownership

**Pinned core [S].** `RenderState.update` decides on a full redraw (screen switch, any `Terminal.flags.dirty` or `Screen.dirty` bit, size change, viewport pin moved), rebuilds only dirty rows (page or row dirty bit), **consumes** the terminal-side bits and leaves `RenderState.dirty` and `row_data[y].dirty` set until the renderer clears them; it never downgrades `dirty` ([P `render.zig#L262-L648`](https://github.com/ghostty-org/ghostty/blob/5714ed07a1012573261b7b7e3ed2add9c1504496/src/terminal/render.zig#L262-L648), sticky logic at L630-647). The native renderer updates once per frame, skips frames while synchronized output (mode 2026) is set, and discards the render state every 100,000 frames to drop retained memory ([P `generic.zig#L1094-L1143`](https://github.com/ghostty-org/ghostty/blob/5714ed07a1012573261b7b7e3ed2add9c1504496/src/renderer/generic.zig#L1094-L1143)).

**Patch [S].** One `RenderState` per terminal (good: a single consumer). `ghostty_render_state_update` additionally frees and recreates the render state on every primary/alternate switch (patch L939-956), which duplicates `update`'s own screen-change check ([P `render.zig#L272`](https://github.com/ghostty-org/ghostty/blob/5714ed07a1012573261b7b7e3ed2add9c1504496/src/terminal/render.zig#L269-L273)) and throws away retained allocations each switch. `mark_clean` clears both layers (patch L1019-1023). Getters size their output from `render_state.rows/cols` (patch L1036-1040, L1247-1249, L1349), while `lib/ghostty.ts` sizes buffers and strides from its own `_cols/_rows` (`:447-464`, `:553-573`): the two agree only because every TypeScript getter calls `update()` first (**SW-08**, design risk).

**TypeScript [S].** `getCursor`, `getLine`, `getScrollbackLine` and `needsFullRedraw` each call `update()` (`lib/ghostty.ts:392-405, 482-491, 552-566, 502-504`). Repeated updates are cheap (§3) and do not lose dirtiness (sticky), so the cost in WEB-01 comes from the full-viewport decode in every `getLine`, not from the updates.

**Current [S].** Same model with `ghostty_render_state_clean`, `row_iterator_next_dirty`, a two-phase `begin_update`/`end_update`, overscan and row ids ([C `render.h#L42-L203`](https://github.com/ghostty-org/ghostty/blob/8f0dd3709050b1026f6324368805033197d8b4a5/include/ghostty/vt/render.h#L42-L203)). Row ids carry the documented guarantee that a row with the same id that is not dirty is unchanged, but "every row is currently marked dirty after the viewport scrolls" ([#L165-L203](https://github.com/ghostty-org/ghostty/blob/8f0dd3709050b1026f6324368805033197d8b4a5/include/ghostty/vt/render.h#L165-L203)), so ids do not yet avoid scroll repaints.

## 3. The bridge's data path: copies, allocations and crossings

### 3.1 What each bridge operation costs structurally [S]

| Operation (`lib/ghostty.ts`)        | Work inside WASM                                                                                     | Copy across the boundary                                   | JS allocations per call                         | Notes                                                                             |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- | ----------------------------------------------- | --------------------------------------------------------------------------------- |
| `write` (`:342-348`)                | parse                                                                                                | input copied into a fresh `wasm_alloc` buffer, freed after | `TextEncoder` + result for string input         | memory may grow inside the parse (§3.5)                                           |
| `readResponse` loop (`:718-734`)    | copy ≤256 B, shift remainder                                                                         | 256 B scratch alloc/free per call                          | `TextDecoder`, string                           | polled after every write (`lib/terminal.ts:1838-1850` per WEB-03)                 |
| `update` (`:384-386`)               | `RenderState.update` (dirty rows only)                                                               | none                                                       | none                                            | called 4+ times per frame (WEB-01); cheap (§3.2)                                  |

| `getLine(y)` (`:482-491`)           | `update` + full `getViewport`                                                                        | as above                                                   | `slice` + `cols` new objects (deep copy)        | called per drawn row, cursor row, hover scan (WEB-01)                             |
| `getScrollbackLine(i)` (`:552-601`) | `update` + page walk from the oldest page + per-cell resolve                                         | 16 B × cols                                                | new array + `cols` new objects                  | addressed by index from the oldest row                                            |

| `getHyperlinkUri` (`:614-653`)      | page lookup                                                                                          | up to 2/8/32 KiB scratch alloc/free                        | `TextDecoder`, string                           | per linked cell; `-1` means both "buffer too small" and "bad coordinates" (SW-10) |

By WEB-01's instrumented counts, a forced 200×50 frame performs 51 full-viewport decodes (510,000 cell decodes); by static reading of `getLine`, the same frame allocates about 51 arrays and 10,200 short-lived cell objects. Report 01's what-if (one decode per frame) and the measurements below agree that the call pattern, not the VT engine, dominates.

### 3.2 Per-frame cost model, best use of each ABI [M] (`sw-frame-cost`)

Workload: a full screen of 256-colour fg+bg text (every 10 cells a new SGR), then either nothing (idle), one character written at row 9 (one dirty row), or a new full screen. Decode target: codepoint + resolved fg + resolved bg into `Uint32Array`s. The VT write is not timed. Mean µs per frame; ranges span two runs.

| Frame type                  | Pinned + patch: `update` + `is_row_dirty`×rows + (`get_viewport` if dirty) + decode dirty rows | Current: `update` + `next_dirty` + `CELLS_RAW` + per-row style cache |
| --------------------------- | ---------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 80×24 idle                  | 0.80–0.88 (Node) · 0.63–0.70 (Bun)                                                             | 0.38–0.41 · 0.33                                                     |
| 80×24 one dirty row         | **22.2–24.3** · **22.3–22.4**                                                                  | **4.1–4.3** · **3.8–4.4**                                            |
| 80×24 full (24 rows dirty)  | 33.5 · 28.0–28.1                                                                               | 41.4 · 53.2–58.2                                                     |
| 200×50 idle                 | 1.04–1.06 · 0.93–0.95                                                                          | 0.25–0.30 · 0.27–0.30                                                |
| 200×50 one dirty row        | **118–119** · **111–112**                                                                      | **6.5–6.9** · **6.5–6.8**                                            |
| 200×50 full (50 rows dirty) | 184–186 · 142                                                                                  | 223–227 · 210–213                                                    |

Both decoders produced identical checksums on the final full frame. Interpretation:

- **SW-06 [M]:** with the patch ABI a one-row change costs 64–80% of a full frame, because `get_viewport` is the only cell getter. With row-scoped reads (current) the cost follows the number of dirty rows. A pinned export of dirty rows from `RenderState.row_data` (§6.4) would use the same row-scoped strategy; its cost was **not** measured because it does not exist yet.
- Idle frames are ≈1 µs of WASM work on both builds; idle cost in ghostty-web is TypeScript-side (WEB-01's never-idle rAF loop, block-cursor `getLine`).
- Full frames on current cost 1.2–2.1× the patch's bulk getter because styles are resolved in JS with extra calls. Report 02 measured 0.70 ms in Bun for this decode with a `DataView`-based decoder; the `Uint32Array` decoder here took 0.21 ms in the same engine. That gap is harness technique, not the ABI, but only part of it is the decoder: swapping just the raw-cell reads to `Uint32Array` in report 02's harness gave 0.54 ms ([report 06](06-verification.md), `v06-bench-frame-extract-u32`). A packed resolved-row export is an optional optimisation (§8), not a prerequisite.

### 3.3 History rows by index vs a Ghostty-owned viewport [M] (`sw-history-fetch`)

80×24, unlimited scrollback, plain text. Pinned: `get_scrollback_line` (one row, fully resolved into 16-B cells, no JS decode). Current: one-row `DELTA` scroll + full `update` + `CELLS_RAW` view for all 24 rows (no JS decode). These measure each ABI's primitive, not equal work.

| History lines | Pinned µs/row at oldest / middle / newest (Node) | Pinned µs per 24-row scrolled frame (Node · Bun) | Current µs per scroll + full update (Node · Bun) | Linear memory high-water, pinned vs current (MiB) |
| ------------- | ------------------------------------------------ | ------------------------------------------------ | ------------------------------------------------ | ------------------------------------------------- |
| 1,000         | 0.67 / 0.67 / 0.67                               | 16.9 · 11.7                                      | 1.6 · 1.4                                        | 8.8 vs 3.9                                        |
| 10,000        | 0.66 / 0.66 / 0.67                               | 17.3 · 12.1                                      | 1.2 · 0.9                                        | 16.8 vs 9.6                                       |
| 100,000       | 0.68 / 0.77 / 0.82                               | 21.0 · 16.2                                      | 1.1 · 0.8                                        | 128.9 vs 68.4                                     |
| 200,000       | 0.65 / 0.83 / 1.03                               | 27.4 · 20.8                                      | 1.1 · 0.8                                        | 256.9 vs 133.7                                    |

The index-from-oldest walk is visible (+55% per row near the newest rows at 200k lines) but small in absolute terms; the larger costs are TypeScript's per-row array allocation and the fact that scrolled frames redraw every row (WEB-01/WEB-09). Ghostty's viewport pin makes scrolled frames independent of history depth. An absolute jump to the middle row plus a scrollbar read on current took 0.3–0.9 µs at every size. A sanity probe (`sw-scroll-sanity`) confirmed that each one-row scroll produced `FULL` dirty with 24 rebuilt rows and the expected first row (≈3.4 µs including per-row dirty reads). Memory: at the same content, the pinned build's linear-memory high-water was 1.75–2.3× the current build's.

### 3.4 Write-path crossing overhead [M] (`sw-write-crossing`)

200,000 small writes (`x?ESC[K`, 5 bytes) into an 80×24 pinned + patch terminal, mean µs per write:

| Pattern                                                                   | Node      | Bun       |
| ------------------------------------------------------------------------- | --------- | --------- |
| A. today's: `new TextEncoder().encode(str)` + alloc + copy + write + free | 0.56–0.76 | 0.32–0.38 |
| B. bytes input + alloc + copy + write + free                              | 0.12      | 0.19      |
| C. persistent input buffer + copy + write                                 | 0.10      | 0.15–0.17 |
| D. persistent buffer + `encodeInto`                                       | 0.12      | 0.15–0.16 |
| E. C + `has_response` poll                                                | 0.10      | 0.21–0.22 |

All variants are sub-microsecond; allocating per write is not a bottleneck. Reusing one `TextEncoder` (or `encodeInto` into a persistent buffer) removes most of A's overhead in V8. The real write-path risks are synchronous parsing of large chunks on the main thread (WEB-17) and memory growth during the parse (§3.5), not crossing cost.

### 3.5 Memory growth, reuse and view invalidation [R] (`sw-memory`)

Linear memory size (`memory.buffer.byteLength`) for the same module instance, 80×24 terminals filled with 30,000 lines (default 10,000-byte budget) or 100,000 lines (10 MB budget). Node and Bun results were identical.

| Step                                                                                 | Pinned + patch (MiB) | Current (MiB)       |
| ------------------------------------------------------------------------------------ | -------------------- | ------------------- |
| fresh instance                                                                       | 1.31                 | 0.63                |
| after first `terminal_new`                                                           | **6.75**             | 1.38                |
| one filled terminal                                                                  | 6.75                 | 1.81                |
| five filled terminals                                                                | **26.75**            | 5.31                |
| after freeing all five                                                               | 26.75                | 5.31                |
| five refilled after free                                                             | 26.75                | 5.31                |
| one terminal, 10 MB budget, 100k lines (history rows retained)                       | 34.81 (9,271 rows)   | 10.19 (13,833 rows) |
| after freeing it / refilling once more                                               | 34.81 / 34.81        | 10.19 / 10.19       |
| `write` calls (64 KiB chunks) that grew memory: first 30k-line fill · 100k-line fill | 0/30 · 2/100         | 1/30 · 8/100        |

- **SW-05 [R]:** at the pinned commit each terminal adds roughly 5 MiB of linear memory as soon as it is created, and nothing is returned on free (it is reused by later terminals). Static cause: each `PageList` preheats four standard pages from `std.heap.page_allocator` ([P `PageList.zig#L25-L31`, #L77-L86, #L283](https://github.com/ghostty-org/ghostty/blob/5714ed07a1012573261b7b7e3ed2add9c1504496/src/terminal/PageList.zig#L25-L31)); upstream replaced this on WASM with a module-wide pool that grows one page at a time ([`492c26067`](https://github.com/ghostty-org/ghostty/commit/492c26067c9f342f46507ade392cfad2e1400360), [C `PageList.zig#L326-L352`](https://github.com/ghostty-org/ghostty/blob/8f0dd3709050b1026f6324368805033197d8b4a5/src/terminal/PageList.zig#L326-L352)). These are high-water marks, not browser RSS; multi-tab embedders pay them per terminal on the pinned build.
- The same byte budget keeps different numbers of rows across versions (9,271 vs 13,833), another reason the public option should be lines (WEB-02).
- Memory grows **inside** `write` and `terminal_new`, so every `ArrayBuffer`/`DataView`/typed-array view held across those calls is detached. This confirms that WEB-05's `KeyEncoder` `DataView` hazard is practical, and it is the first rule of the ABI in §6.3. Upstream documents the same rule ([C `wasm.h#L39-L47`](https://github.com/ghostty-org/ghostty/blob/8f0dd3709050b1026f6324368805033197d8b4a5/include/ghostty/vt/wasm.h#L39-L47)).
- WEB-02's `scrollback: 0` = unlimited remains the dangerous combination: one terminal can grow the shared heap without bound, and the memory is never returned to the page.

Corrections and refinements to [report 02](02-upstream-architecture.md):

1. **"Per-cell C API too chatty; JSC ~4.6× slower than one bulk copy, motivating a packed resolved-row export"** — the 4.6× JSC figure is harness-sensitive; this report's harness (typed-array decoder, cached palette, dirty-row iterator) measured the same full-frame work at 210–213 µs vs 142 µs for the patch getter in Bun (1.5×). _(Verification note, [report 06](06-verification.md): the decoder swap alone explains only 0.69 → 0.54 ms of the difference; the original wording attributed all of it to `DataView`.)_ Report 02's core point (avoid per-cell calls) stands; the packed export moves from "motivated" to "optional, measure in browsers first".
2. **"`linkCells` defect … not reproduced (would require a page-spanning viewport probe)"** — page-spanning is not required. `Page.getRowAndCell` takes page-relative coordinates, and the viewport's first row is page row 0 only before the first page has scrolled; upstream's fix says it read "the wrong cell even in single-page scenarios" ([`5a2f5a6b9`](https://github.com/ghostty-org/ghostty/commit/5a2f5a6b9e87d2d3324dbcb4022cb02df4db8d6e)). Still static here (the patch exports no `linkCells`).
3. **Report 02 §5.2 rule 3 ("viewport scroll ⇒ full dirty")** is confirmed for current upstream by `sw-scroll-sanity` and follows from pinned `render.zig#L297-L300`; row ids therefore do not yet let a renderer skip repainting after a scroll on either version.

## 6. Proposed versioned ABI and adapter (PROPOSED)

Nothing in this section exists today. It is a design that another engineer can implement and compile-check; field widths and offsets are a starting point, not a frozen layout.

### 6.1 Design principles

1. **Ghostty owns state; JavaScript owns policy.** Viewport position, selection, row identity, link identity, dirty tracking and query replies live in WASM. Gestures, scroll-on-output policy, link opening, clipboard, drawing and timers stay in TypeScript.
2. **One crossing per concern.** One `frame` call per animation frame and one event drain per `write`; no per-row or per-cell calls on hot paths (per-cell calls measured 15–20× a bulk read in report 02).
3. **Self-describing, versioned layouts.** A manifest with the same schema as upstream's `ghostty_type_json`, so a single manifest-driven decoder serves both backends.
4. **Borrowed memory has an explicit lifetime** and a generation counter; nothing borrowed survives a mutating call.
5. **Positions that outlive a mutation are handles** (tracked pins/grid refs) or opaque ids, never numeric row indices.
6. **Same TypeScript interface for both backends**, so the pinned → current move is a backend swap with the same tests.

### 6.2 Naming, versioning and feature negotiation

- **Prefix every ghostty-web-owned export with `ghostty_web_`.** Today's patch defines `ghostty_terminal_new(cols, rows)` and `ghostty_render_state_update(term)`, which collide with upstream exports of the same names and different signatures ([report 02 §2.3](02-upstream-architecture.md#23-consequence-rebasing-means-replacing-not-porting)). Prefixed names let a rebased build carry upstream's API and a small residual patch side by side.
- **`ghostty_web_abi_json() -> const char*`** (PROPOSED): NUL-terminated JSON with upstream's manifest shape (`schema`, `abi` {pointer size, alignment, endianness}, `types` with struct sizes/field offsets/enum values) plus `web_abi: {major, minor, features[], ghostty_commit, patch_sha256}`. Our current build reports `commit: null` in `ghostty_type_json`, so the commit must be stamped by the build script, not assumed.
- **Negotiation in the adapter:** `major` must equal the adapter's; `minor` must be ≥ the minimum; `features` gate optional capabilities (`frame.v1`, `colors.tagged`, `links.key`, `viewport.scroll`, `selection`, `search`, `events`, `modes.snapshot`, `rows.id`, `overscan`, `memory.stats`). Fail loudly at load on a mismatch (WEB-15's missing handshake).
- **Upstream backend:** derive the same capability set from export presence, `ghostty_build_info` (simd, kitty graphics, optimize, version; [C `build_info.h#L53-L126`](https://github.com/ghostty-org/ghostty/blob/8f0dd3709050b1026f6324368805033197d8b4a5/include/ghostty/vt/build_info.h#L53-L126)), `ghostty_type_json`, and the pinned upstream commit recorded at build time. Note that `-Dvt-features` subsets remove exports, so presence checks are required.

### 6.4 Frame snapshot and delta format

`ghostty_web_frame(term, flags, const GhosttyWebFrame **out)` performs exactly one `RenderState.update` and writes one **contiguous** buffer owned by the terminal: header, row records (which double as the dirty-row list), cells, grapheme side table, palette (only when changed) and string pool. A partial frame contains only dirty rows (the delta); a full frame contains all rows. `ghostty_web_frame_clean(term)` clears both dirty layers after the renderer has drawn (upstream semantics: `update` never clears; dirt accumulates across frames that were not drawn). Because the buffer is contiguous, a future Worker backend can transfer it with one `slice` and `postMessage`.

```c
/* PROPOSED — illustrative layout, little-endian, all offsets relative to the frame start */
typedef struct {
  uint32_t size;                 /* sized-struct pattern, as upstream */
  uint16_t abi_major, abi_minor;
  uint32_t seq;                  /* +1 per frame(); borrowed data valid while unchanged */
  uint8_t  dirty;                /* 0 none, 1 partial, 2 full */
  uint8_t  screen;               /* 0 primary, 1 alternate */
  uint16_t flags;                /* viewport_active, sync_output(2026), cursor_visible, cursor_blinking,
                                    cursor_password, cursor_in_viewport, cursor_wide_tail,
                                    selection_present, vt_error_sticky, palette_changed */
  uint16_t cols, rows, cursor_x, cursor_y;
  uint8_t  cursor_style;         /* bar, block, underline (renderer adds hollow when unfocused) */
  uint8_t  mouse_shape;          /* OSC 22 */
  uint16_t row_count;            /* rows included in this frame */
  uint32_t default_fg, default_bg, cursor_color;   /* tagged colours (below) */
  uint64_t scroll_total, scroll_offset;            /* PageList.scrollbar() */
  uint32_t scroll_len;
  uint32_t modes[2];             /* snapshot bitset: DECCKM, keypad, 2004, 1004, 1007, mouse event
                                    and format modes, kitty flags (5 bits), modifyOtherKeys, 2027 … */
  uint32_t off_rows, off_cells, off_graphemes, off_palette, off_strings, total_bytes;
} GhosttyWebFrameHeader;

typedef struct {                 /* 24 bytes */
  int16_t  y;                    /* viewport y (negative/≥rows reserved for overscan) */
  uint16_t flags;                /* wrap, wrap_continuation, has_graphemes, has_links, semantic prompt (2 bits) */
  uint16_t sel_start, sel_end;   /* 0xFFFF = no selection on this row */
  uint64_t id_serial;            /* row id = (page serial, page-local y): never reused */
  uint16_t id_y, grapheme_count;
  uint32_t grapheme_off;
} GhosttyWebRow;

typedef struct {                 /* 24 bytes = 6 × u32, read with a Uint32Array */
  uint32_t cp;                   /* bits 0-20 codepoint, 21-22 width class, 23 has_grapheme */
  uint32_t fg, bg, ul;           /* tagged colour: tag in bits 24-31 (0 default, 1 palette idx, 2 rgb) */
  uint32_t attrs;                /* bold, italic, faint, blink, inverse, invisible, strike, overline,
                                    underline style (3 bits), protected */
  uint32_t link;                 /* 0 = none, else 32-bit link key (below) */
} GhosttyWebCell;
```

Design notes:

- **Tagged colours** keep "explicit black" distinct from "default" (WEB-04) and leave policy to the renderer: bold-is-bright, minimum contrast, inverse, selection colours and runtime theme changes resolve against the palette sent with the frame (only when `palette_changed`). Background must be derived with `Style.bg` semantics from the raw content tag first (SW-09).
- **Full attributes** add underline style/colour and overline (WEB-11). Width classes include spacer head/tail, so text extraction can skip spacers (WEB-08).
- **Graphemes** come from `RenderState.Cell.grapheme`, which is correct for scrolled rows (fixes WEB-09's wrong-row lookup).
- **Link key.** A 32-bit hash of `(id kind, explicit id bytes or implicit value, URI)` computed in WASM per hyperlink entry and cached per page entry during the frame build. It is stable across frames and pages because it is derived from the same fields `PageEntry.eql` compares ([P `hyperlink.zig#L161-L186`](https://github.com/ghostty-org/ghostty/blob/5714ed07a1012573261b7b7e3ed2add9c1504496/src/terminal/hyperlink.zig#L161-L186)), so partial frames stay consistent with rows drawn earlier. A collision only mis-highlights hover; clicking always re-reads the URI at the clicked cell. This replaces exporting `linkCells` (SW-03) and works the same on both backends.
- **Row ids** use the page serial and page-local `y`, which already exist at the pinned commit (§2.1). They are cache keys only: a renderer may reuse a cached row only if the id matches **and** the row is not dirty (upstream's contract).
- **Size.** A full 200×50 frame is 240 KB of cells plus row records; the buffer is retained per terminal and only grows on resize. Overscan (smooth scrolling) is a current-upstream feature; on the pinned backend the flag is absent and scrolling moves in whole rows.
- **Alternative considered:** 12–16-byte cells referencing a per-frame style table. Smaller, but adds an indirection per cell in JavaScript and a second table to keep coherent across partial frames; deferred until browser measurements show frame size matters.

### 6.6 Event queue

On the pinned backend the stream handler appends records to a per-terminal buffer during `write`; `ghostty_web_events(term, &ptr, &len)` exposes it and `ghostty_web_events_clear(term)` resets it. The adapter copies the bytes once per write and dispatches in order.

- **Record:** `u16 type, u16 flags, u32 len, payload`, padded to 4 bytes. Types: `PTY_REPLY`, `BELL`, `TITLE`, `PWD`, `CLIPBOARD_WRITE`, `CLIPBOARD_READ`, `NOTIFICATION`, `PROGRESS`, `MOUSE_SHAPE`, `SYNC_OUTPUT` (begin/end), `RESET`, `COLORS_CHANGED`.
- **Order** is stream order, so reply ordering is preserved (concatenate `PTY_REPLY` payloads).
- **Bounds:** a per-terminal byte cap with an overflow counter; when full, coalesce `TITLE`/`PWD` (last wins) and `BELL` (count). Time-sliced writes in TypeScript (WEB-17) bound the volume one write can generate.
- **Render holds:** at pinned, mirror native: while the `sync_output` header bit is set, do not call `frame` and keep the last drawn canvas, with an embedder-owned timeout ([P `generic.zig#L1136-L1140`](https://github.com/ghostty-org/ghostty/blob/5714ed07a1012573261b7b7e3ed2add9c1504496/src/renderer/generic.zig#L1136-L1140)). On current, upstream's `RENDER_HOLD` contract requires updating the render state **inside** the callback at hold start ([C `terminal.h#L1638-L1756`](https://github.com/ghostty-org/ghostty/blob/8f0dd3709050b1026f6324368805033197d8b4a5/include/ghostty/vt/terminal.h#L1638-L1756)), so the adapter needs one synchronous hook there. _(Verification note, [report 06](06-verification.md): the original sentence said every other effect can be queued.)_ Clipboard reads are a second exception: on current, `clipboard_read` must be answered by calling `reply` before the callback returns, otherwise the read is denied ([C `terminal.h#L1024-L1036`](https://github.com/ghostty-org/ghostty/blob/8f0dd3709050b1026f6324368805033197d8b4a5/include/ghostty/vt/terminal.h#L1024-L1036)), and browser clipboard reads are asynchronous. A queued `CLIPBOARD_READ` at pinned that JavaScript answers later would put its reply after the replies to queries that came later in the same write. Deny by default, or answer synchronously from a JS-held value; [report 05](05-input-and-protocols.md) covers the policy. Every other effect can be queued.
- **Why a queue, not callbacks, at pinned:** no function-table trampolines, one crossing per write, no re-entrancy hazards, and identical behaviour in a Worker. On current, callbacks are the public mechanism; the adapter pushes them into the same JS-side queue.

### 6.8 TypeScript adapter boundary

```ts
// PROPOSED — backend-neutral; only implementations know export names and layouts.
interface CoreBackend {
  readonly capabilities: ReadonlySet<Capability>;
  create(config: CoreConfig): CoreTerminal;
}
interface CoreTerminal {
  write(bytes: Uint8Array): CoreEvent[]; // events drained once per write
  resize(cols: number, rows: number, cellPx: { w: number; h: number }): void; // throws on failure
  reset(): void;
  frame(): Frame; // one update; header + included rows
  clean(): void; // after drawing
  scroll(kind: 'top' | 'bottom' | 'delta' | 'row', value?: number): void;
  anchor(point: Point): Anchor; // tracked; anchor.get() may return null
  select(sel: SelectionRequest): void; // between | word | line | all | output | clear
  selectionText(opts: { unwrap: boolean; trim: boolean }): string;
  linkUriAt(point: Point): string | null; // click path; hover uses Frame link keys
  encodeKey(e: KeyInput): Uint8Array | null; // terminal-state-aware (other reports)
  encodeMouse(e: MouseInput): Uint8Array | null;
  dispose(): void;
}
interface Frame {
  seq: number;
  dirty: 'none' | 'partial' | 'full';
  cols: number;
  rows: number;
  cursor: CursorState;
  colors: FrameColors;
  scrollbar: Scrollbar;
  modes: ModeSnapshot;
  includedRows(): Iterable<FrameRow>; // dirty rows for partial frames, all rows for full
}
```

- **Pinned v2 backend:** thin decoding over the contiguous frame buffer; `CoreEvent`s parsed from the queue.
- **Upstream backend:** builds `Frame` from `ghostty_render_state_*` (`next_dirty`, `CELLS_RAW`, per-row style cache keyed by row, `DATA_COLORS`, `DATA_CURSOR`), reads `DATA_SCROLLBAR` and modes in the same turn, computes link keys from URIs of `has_hyperlink` cells (or from a residual export), and turns callbacks into `CoreEvent`s.
- **Above the boundary** (shared by both): `Terminal` (xterm.js facade), renderer, input handler, selection gestures, scroll policy, link providers, paste policy.
- **Testing:** run one behavioural suite against both backends (backend matrix), using the acceptance tests in §9.

### 7.3 Recommendation and trade-offs

- Build the **`CoreBackend` adapter first** (report 02's option C), with the frame/event model above. Most of the code ghostty-web must write — the frame consumer, scroll and selection policy, event dispatch, the backend-matrix tests — is the same for both backends.
- Implement **pinned v2 phase A** behind it now: it fixes the measured frame-cost problem (SW-06), the viewport and grapheme defects (WEB-09), colours (WEB-04) and lifecycle issues, with modest core risk. Use delta-only scrolling or the tiny `u16` backport.
- Do **phase B (selection)** at pinned only if the rebase is more than about one cycle away; SW-07 shows TypeScript indices cannot be fixed without tracked positions.
- Develop the **upstream backend in parallel** and switch when the upstream API is tagged or a `main` commit is validated. The residual patch is small (link identity, `mouse_shift_capture`, optional extras).
- Rejected: porting upstream's C API files to pinned (depends on post-pinned core); exporting pinned `linkCells` (SW-03); exporting pinned `scroll(.row)` unpatched (SW-02); function-table callbacks at pinned (a queue is simpler and Worker-friendly).

## 10. Benchmark methodology

**Three separate layers; never mix them in one number.**

1. **Parse throughput (WASM only):** report 02's `bench-vt-write.mjs` corpora (ASCII, SGR-heavy, UTF-8 mixed, cursor-addressed), 16 KiB writes, fresh terminal per run.
2. **Frame extraction (WASM + JS decode, no canvas):** `sw-frame-cost.mjs`, extended to idle / one dirty row / ten dirty rows / full / one-row scroll, at 80×24, 120×40, 200×50 and 250×70, for both backends, with a checksum proving equal decoded output.
3. **Browser end-to-end:** Playwright on Chromium, Firefox and WebKit, DPR 1, 1.25 and 2, fixed byte corpora (large `cat`, htop-like cursor updates, vim scrolling, CJK/emoji text). Metrics: rAF-to-rAF frame time, long tasks (`PerformanceObserver('longtask')`), keydown-to-paint latency for echo, `memory.buffer.byteLength`, and JS heap where the browser exposes it.

**Rules.** Setup outside the timed region; warm-up; at least 7 runs; report median and p95 with raw JSON; interleave backends; equal work proven by checksums; same machine for any comparison, with browser, OS and power settings recorded; label WASM-only results as such; do not compare a per-cell API against a bulk API with different decode targets; record decoder technique (`DataView` vs typed arrays), which changed JSC results by more than 3× here.

**Proposed targets (to validate, not measured claims):** one-row partial frame data path ≤10% of a full frame at 200×50; zero WASM calls per animation frame when nothing is dirty and no blink is active; linear memory per additional filled default terminal ≤1 MiB after the rebase.

## 11. Dependencies, risks and confidence

**Dependencies.** The event queue and handler composition (A9) are specified by the effects/input report; mouse/key encoders depend on the frame's mode snapshot; the renderer must consume tagged colours, link keys and row records; real-browser measurements are needed before any packed-row or blit optimisation.

**Risks.**

- **Pinned core drift.** Between pinned and current there are 116 commits to `PageList.zig`, 87 to `Screen.zig`, 31 to `page.zig`, 23 to `formatter.zig`, 17 to `render.zig`, 8 to `Selection.zig` and 38 under `search/`. Fixes in exactly the paths this ABI would export include, besides SW-01–SW-04: tracked pins on non-standard pages ([`b99559595`](https://github.com/ghostty-org/ghostty/commit/b995595953bdd7d6537a553827308c803539f49d)), total-row and pin accounting during page reuse ([`509f07336`](https://github.com/ghostty-org/ghostty/commit/509f0733667d7631266f787ea800ba05d3672cec)), word selection across wide characters ([`a3e80a685`](https://github.com/ghostty-org/ghostty/commit/a3e80a685ed672873aefe8bb07b8516ec3a4175a)) and full row-metadata reset on recycling ([`b31fbc846`](https://github.com/ghostty-org/ghostty/commit/b31fbc846474bf6082f1a3f13290e17f2d984a25), the upstream replacement for the patch's `Screen.zig` edit per report 02). Command: `git log --oneline 5714ed07..8f0dd370 -- src/terminal/PageList.zig src/terminal/Screen.zig src/terminal/render.zig src/terminal/Selection.zig src/terminal/page.zig | grep -iE 'fix|crash|stale|invalid'`.
- **Undefined behaviour in ReleaseSmall.** Integrity assertions are compiled out; SW-01 showed an invalid state without a trap. Running the stale-row, resize and prune stimuli against a ReleaseSafe or slow-runtime-safety build was not done here and is recommended.
- **Upstream API churn.** Untagged and documented as unstable; mitigated by manifest-driven bindings, load-time checks and the adapter boundary.
- **Frame-buffer size and copies.** Unmeasured in browsers; a full frame is a ≤240 KB copy at 200×50.
- **Link-key collisions.** 32-bit hashes can collide (hover only); clicks re-read the URI.

**Confidence.**

- **High:** state-ownership facts in §2 (read at source with line anchors); probe results SW-01, SW-05, SW-07, tracked-ref behaviour and the 70,000-row jump (deterministic, identical in Node and Bun); the structural cost analysis in §3.1.
- **Medium:** relative frame costs in §3.2–3.4 (two runs per engine, consistent; WASM-only, single machine); the line-count estimates in §7.1; the claim that a pinned dirty-row export closes most of the SW-06 gap (by analogy with current's measured row-scoped path, not measured).
- **Low / unverified:** browser impact of any of these numbers; whether `86d5048da` and `815ccb060` apply cleanly to pinned; real-world impact of SW-01 beyond the invalid cell (no trap observed); link-key behaviour across terminal resets with implicit ids.

## 12. Open questions

1. Will upstream accept a hyperlink identity export (per-cell link key or `linkCells` over the render state), and a getter for non-active screen rows?
2. Can row ids carry a "content unchanged, only moved" signal so renderers can skip repainting after scrolls (upstream currently marks every row dirty)?
3. Is a WASM-only reduction of `page_preheat` safe at pinned as a stop-gap for SW-05, or should multi-terminal embedders wait for the rebase?
4. What frame cost does a Canvas2D or WebGL renderer add on top of the data path in §3.2, at DPR 2 and 250×70? This decides whether the packed-row export or blit hints matter.
5. Should ghostty-web expose `scrollbackBytes` alongside an approximate `scrollback` line count, given page-granular retention in both versions?
6. Is one instance per terminal (trap isolation) affordable once the rebase brings per-terminal memory under 1 MiB?
